# 小说原文 RAG 本地知识库 PRD

版本：v0.2  
日期：2026-07-02  
当前语料：《轮回乐园》原文  
目标形态：可迁移到其他小说的本地网页 RAG

## 1. 项目背景

当前目录中已有《轮回乐园》原文 txt 文件，用户希望基于原文建立 RAG 知识库，用于严格依据原文回答问题。后续该流程需要可复用到其他小说，例如输入《西游记》原文后，可以用同一套流程建立新的小说 RAG。

本阶段重点不是游戏生成，也不是二创策划，而是先把“依据原文问答”的底座做好，包括原文解析、切分、索引、检索、引用和本地网页查询。

## 2. 已确认需求

1. 使用范围：本地个人使用。
2. 产品形态：本地网页。
3. 模型策略：
   - MVP 优先使用本地小模型，例如 Ollama。
   - 后期对回答质量要求更高时，可切换到 API 模型。
4. 当前输出目标：严格考据，回答必须依据原文。
5. 游戏方向：后期参考小说机制进行游戏开发，但当前阶段暂不展开游戏设计功能。
6. 可迁移性：流程应支持替换小说原文，构建新的 RAG 知识库。

## 3. MVP 目标

建立一个本地运行的小说 RAG 网页，用户可以：

1. 选择一个小说项目。
2. 导入该小说的 txt 原文。
3. 自动解析章节。
4. 构建本地向量索引。
5. 在网页中提问。
6. 获得严格依据原文的回答。
7. 查看引用来源，包括章节号、章节标题、命中文本片段。

## 4. 非目标

MVP 暂不做：

1. 游戏机制生成。
2. 角色卡自动生成。
3. 多人协作。
4. 在线部署。
5. 商业化发布。
6. 直接复述大段原文。
7. 复杂知识图谱。
8. 自动处理 PDF、EPUB、图片 OCR。

## 5. 用户场景

### 5.1 严格考据问答

用户提问：

```text
轮回乐园中，苏晓第一次接触乐园是在什么情况下？
```

系统返回：

```text
根据第1章《复仇者》，苏晓是在濒死状态下接触到轮回乐园，并看到乐园相关提示。当前检索结果只能确认这个具体个案，不能推断所有人进入乐园的通用规则。

引用：
- 第1章 复仇者
```

### 5.2 章节定位

用户提问：

```text
斩龙闪最早出现在哪些章节？
```

系统返回相关章节、片段摘要和置信度。

### 5.3 设定查询

用户提问：

```text
乐园币、属性点、技能升级之间有什么关系？
```

系统仅基于检索到的章节回答。如果证据不足，需要明确提示“当前检索结果不足以完整回答”。

## 6. 内容和版权边界

该系统定位为本地个人学习与资料查询工具。回答策略应遵守：

1. 不输出长篇原文。
2. 不把小说原文作为公开接口对外提供。
3. 引用片段仅用于定位和核验。
4. 后续游戏开发时，应抽象机制和结构，避免直接复刻原文角色、剧情、台词和专有表达。

## 7. 当前语料情况

当前原文目录：

```text
原文/
  轮回乐园(1-500章).txt
  轮回乐园(501-1000章).txt
  轮回乐园(1001-1500章).txt
  轮回乐园(1501-2000章).txt
  轮回乐园(2001-2500章).txt
  轮回乐园(2501-3000章).txt
  轮回乐园(3001-3500章).txt
  轮回乐园(3501-4000章).txt
  轮回乐园(4001-4189章).txt
```

初步观察：

1. txt 总大小约 46.8 MB。
2. 文件应按 UTF-8 读取。
3. 章节标题可以通过 `第N章 标题` 识别。
4. 每章标题存在重复行，需要导入时去重。
5. 文件名章节范围与实际章节检测结果存在偏差，需要做章节连续性校验。

## 8. 通用小说项目模型

为支持后续迁移到其他小说，系统不应把《轮回乐园》写死。建议采用项目配置：

```json
{
  "project_id": "reincarnation_paradise",
  "display_name": "轮回乐园",
  "source_dir": "原文",
  "encoding": "utf-8",
  "chapter_patterns": [
    "^第([0-9一二三四五六七八九十百千万]+)章\\s*(.*)$"
  ],
  "remove_duplicate_chapter_title": true,
  "chunk_size": 1000,
  "chunk_overlap": 200,
  "language": "zh"
}
```

后续《西游记》可新增：

```json
{
  "project_id": "journey_to_the_west",
  "display_name": "西游记",
  "source_dir": "原文/西游记",
  "encoding": "utf-8",
  "chapter_patterns": [
    "^第([0-9一二三四五六七八九十百千万]+)回\\s*(.*)$"
  ],
  "remove_duplicate_chapter_title": false,
  "chunk_size": 1000,
  "chunk_overlap": 200,
  "language": "zh"
}
```

## 9. 数据处理流程

### 9.1 原文读取

输入：小说项目目录中的 txt 文件。  
输出：原始文本列表。

要求：

1. 固定使用项目配置中的编码读取。
2. 保留原始文件名。
3. 记录文件大小和读取状态。
4. 读取失败时给出明确错误。

### 9.2 章节解析

输入：原始文本。  
输出：`chapters.jsonl`。

要求：

1. 根据配置中的章节正则识别章节。
2. 章节号转成统一数字。
3. 章节标题去除首尾空白。
4. 对重复章节标题行去重。
5. 记录章节来源文件。
6. 生成章节连续性报告。

章节数据结构：

```json
{
  "project_id": "reincarnation_paradise",
  "chapter_no": 1,
  "chapter_title": "复仇者",
  "source_file": "轮回乐园(1-500章).txt",
  "text": "章节正文"
}
```

### 9.3 文本清洗

清洗规则：

1. 移除网址、来源站点、明显广告行。
2. 移除重复章节标题。
3. 保留正文段落。
4. 保留系统提示、属性面板、任务描述、装备描述等设定信息。
5. 不做激进改写，避免破坏原文证据。

### 9.4 切分

输入：章节文本。  
输出：`chunks.jsonl`。

默认策略：

1. 先按章节切。
2. 章节内按段落聚合。
3. chunk 大小约 1000 中文字。
4. overlap 约 200 中文字。
5. 每个 chunk 必须携带章节元数据。

切片结构：

```json
{
  "chunk_id": "reincarnation_paradise_ch0001_0001",
  "project_id": "reincarnation_paradise",
  "chapter_no": 1,
  "chapter_title": "复仇者",
  "source_file": "轮回乐园(1-500章).txt",
  "chunk_index": 1,
  "text": "切片正文"
}
```

### 9.5 向量索引

MVP 推荐：

1. 向量库：Chroma 或 FAISS。
2. Embedding：优先使用 Ollama 本地 embedding 模型。
3. 索引按 `project_id` 隔离。
4. 支持删除并重建单个小说项目索引。

备选 embedding：

1. Ollama `bge-m3` 或同类中文向量模型。
2. 后期 API embedding 模型。

### 9.6 检索

MVP 检索策略：

1. 向量检索 Top K = 8。
2. 可选关键词召回 Top K = 8。
3. 合并去重。
4. 暂不强制 rerank，后期可增加 reranker。
5. 最终传给 LLM 的上下文数量默认 4 到 6 个 chunk。

## 10. 回答策略

系统提示词核心要求：

1. 只能根据提供的原文片段回答。
2. 原文片段不足时，必须说明“当前证据不足”。
3. 不要编造章节、人物关系或设定。
4. 回答后列出引用章节。
5. 不输出大段原文。
6. 对推断内容需要标明“这是基于片段的推断”。

推荐回答格式：

```text
回答：
...

依据：
- 第N章《章节标题》：简要说明该章节支持了什么结论
- 第M章《章节标题》：简要说明该章节支持了什么结论

不确定点：
- 当前检索结果不足以确认...
```

## 11. 本地网页功能

MVP 页面包含：

1. 项目选择区
   - 当前项目名
   - 原文目录
   - 索引状态

2. 索引管理区
   - 扫描原文
   - 解析章节
   - 构建索引
   - 查看章节校验报告

3. 问答区
   - 问题输入框
   - 查询按钮
   - 模式选择：严格考据
   - Top K 设置
   - 温度设置，默认低温

4. 结果区
   - 回答正文
   - 引用章节
   - 命中片段
   - 置信提示

## 12. 技术建议

MVP 技术栈建议：

1. 后端：Python + FastAPI。
2. 前端：轻量本地网页，可用原生 HTML/CSS/JS 或 Vue。
3. 向量库：Chroma。
4. LLM：Ollama。
5. Embedding：Ollama embedding 模型。
6. 数据格式：JSONL。

## 13. Ollama 配置建议

MVP 可采用：

1. 生成模型：`qwen2.5:7b`、`qwen3:8b`、`llama3.1:8b` 等本地模型。
2. Embedding 模型：优先选择支持中文的 embedding 模型，例如 `bge-m3` 相关模型。

模型配置应写在配置文件中，便于后期切换 API：

```json
{
  "llm_provider": "ollama",
  "llm_model": "qwen2.5:7b",
  "embedding_provider": "ollama",
  "embedding_model": "bge-m3",
  "temperature": 0.2,
  "top_k": 8,
  "context_chunks": 5
}
```

## 14. API 设计草案

### 14.1 查询项目列表

```http
GET /api/projects
```

### 14.2 扫描原文

```http
POST /api/projects/{project_id}/scan
```

### 14.3 构建索引

```http
POST /api/projects/{project_id}/index
```

### 14.4 提问

```http
POST /api/projects/{project_id}/query
```

请求：

```json
{
  "question": "苏晓第一次接触轮回乐园是在什么情况下？",
  "mode": "evidence",
  "top_k": 8
}
```

响应：

```json
{
  "answer": "根据第1章《复仇者》...",
  "citations": [
    {
      "chapter_no": 1,
      "chapter_title": "复仇者",
      "chunk_id": "reincarnation_paradise_ch0001_0001"
    }
  ],
  "retrieved_chunks": []
}
```

## 15. 验收标准

MVP 完成后应满足：

1. 能在本地网页打开系统。
2. 能识别当前《轮回乐园》原文目录。
3. 能解析章节并生成 `chapters.jsonl`。
4. 能生成 `chunks.jsonl`。
5. 能构建本地向量索引。
6. 能通过网页提问并获得回答。
7. 回答必须附带章节引用。
8. 检索证据不足时不会强行编造。
9. 能查看章节连续性和异常报告。
10. 能通过新增项目配置迁移到另一部小说。

## 16. 风险和处理

### 16.1 章节识别不稳定

不同小说章节格式不同。  
处理：章节正则配置化，并输出解析报告。

### 16.2 本地小模型回答质量有限

Ollama 小模型可能出现遗漏或编造。  
处理：低温度、强提示词、显示引用片段、后期可切 API 模型。

### 16.3 长篇小说检索跨度大

单纯向量检索可能漏掉关键设定。  
处理：后期增加关键词检索、rerank、实体索引。

### 16.4 原文质量问题

可能存在错章、缺章、重复章节、广告文本。  
处理：导入阶段生成异常报告，人工确认后再重建索引。

## 17. 后续迭代方向

MVP 之后可以扩展：

1. 混合检索：向量 + BM25。
2. Reranker：提高精确度。
3. 实体抽取：角色、道具、地点、势力、技能。
4. 时间线：按章节整理事件。
5. 角色档案：自动汇总角色信息。
6. 小说迁移向导：上传新小说后自动推荐章节正则。
7. AI 工作流：原文导入、章节解析、索引构建、问答测试一键执行。
8. API 模型切换：本地模型和云端模型共用同一接口。

## 18. 推荐开发顺序

1. 建立项目配置文件。
2. 编写原文扫描和章节解析脚本。
3. 生成章节校验报告。
4. 编写 chunk 切分脚本。
5. 接入 Ollama embedding 并构建 Chroma 索引。
6. 编写命令行 query 验证检索质量。
7. 编写 FastAPI 后端。
8. 编写本地网页。
9. 用 10 到 20 个问题测试回答和引用质量。
10. 调整 chunk、Top K、提示词和模型配置。
